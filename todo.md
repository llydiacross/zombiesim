# Phase B 2 (Done)

4. Border Variations
 - Calification: Unlike how we deal with buildings, the a is actually a randomness factor instead and is meant to signal variation. Also, there might be more than 1 and maybe 2 or more. So its essentially just supposed to be treated as a huge pool of random borders to improve variation.
 - Renamed `wallTemplatesByDensity` to `wallVariationTemplates` (config + `build_cell_vmfs.ps1`) and replaced the density-tier index with a deterministic per-slot hash pick (`Get-RandomWallVariationTemplate`, keyed on placementSeed+tileX+tileY) across the whole pool, so a single cell's ring mixes `tile_border_wall`/`_1a`/`_1aa`/`_1aaa` (and the military/radioactive profile pools) instead of picking one variant for the entire ring. Verified a sample generated cell uses all 4 base variants across its ring.

 - The border water assets: They do exist! Please see the file "tile_border_water_deadend.vmf" in tiletemplates/border and its various pieces. The hammer authored tiles are right there.
 - Implemented: added `vmfBuild.border.water` config (enabled/chancePercent/cornerSpan/pierEveryTiles + deadend/none/pier/corner templates). Per world generation, one of the four map corners is deterministically chosen (or none, per `chancePercent`) from the map seed. Cells within `cornerSpan` of that corner's two boundary edges get their outward-facing wall ring reskinned: mostly `tile_border_water_none.vmf` with periodic `tile_border_water_pier_1/2.vmf`, the exact map-corner cell's ring corner becomes `tile_border_water_pier_corner.vmf`, and the far tip of each runway caps back to land with `tile_border_water_deadend.vmf`.
 - This is world-position-dependent, which conflicts with this generator's recipe deduplication (many world cells normally share one physical generated VMF by content signature alone). Fixed by computing water-border participation once in `plan_cell_templates.ps1` (which has the map seed/grid size) and folding it into each affected cell's filename (`-wtr<sides>`) so corner cells get their own uniquely-generated file instead of silently sharing a non-water recipe elsewhere on the map; `build_cell_vmfs.ps1` now just consumes the precomputed `Recipe.waterBorderSides` instead of recomputing/guessing. Verified end to end at a forced 100% chance: the exact selected-corner cell got `tile_border_water_pier_corner.vmf`, and both runway tips got `tile_border_water_deadend.vmf`.

 - In the generated multi zoo, a commercial building is facing the opposite direction than intended to the concrete path and appears backwards to the vertical path.
 - Root cause: `Get-MarkedRoadConnectionCandidates` in `plan_cell_templates.ps1` only rejected a building from facing the *side* of a straight ordinary road (as opposed to its open ends) — the same axis check was never applied to straight concrete paths (or, in the no-`zn_road_connection`-marker fallback branch, to anything at all), so a single-tile building could rotate to face the long side of a vertical concrete path instead of only its N/S ends. Added the same rotationYaw-axis rejection for concrete paths in both the marker-based and non-marker candidate search branches.

- A different bug found via the border showcase: the 2x building `tile_building_1b_2x` (`zm_tile_building_3_0` in `zn_gr_rs-v-d1_n-m22-b1b-p3-0-q0-cp.vmf`) was rotated 180 degrees off, facing away from the road it should front onto.
- Root cause: Phase A's canonical `zn_tile_direction` origin formula had `east`/`west` backwards relative to the grid/rotation system. `north`/`south` already matched (grid `S` = +tileY = world -Y = "south", matching the formula's `south=(0,-edge)`), but the formula's `east=(-edge,0)` is world **negative** X, while the grid's own `E` direction (used by `Get-DirectionToCoordinate`/`Get-BuildingEntranceRotation` to actually rotate buildings toward roads) is world **positive** X (`E` = +tileX = +worldX). Updated `docs.md`'s canonical-origin table to match. Verified: the same cell's building instance now emits `angles "0 0 0"` (previously `180`), correctly facing the road on its west side. `test_multi_tile_templates.ps1` and `test_border_showcase.ps1` both still pass.

- Root cause: `tile_building_1b_2x`'s own `zn_road_connection` marker has `connection_type "none"` (inert — it doesn't actually request a T-junction), so its multi-tile placement went through the generic fallback candidate search (`Get-FootprintRoadFacingCandidates`/`Test-RoadPlacementFacesCoordinate`), not the strict marked-connection path. That fallback accepted ANY adjacent tile with a road-ish role as valid frontage, including a `road`-role `tile_road_deadend.vmf` from its *closed* side — unlike the marked-connection path (fixed in Phase B2), it never checked whether the road placement's own directionality actually faced the building.

Verified: the same building now anchors at `(0,0)` instead of next to the deadend at `(3,1)`. `test_border_showcase.ps1`, `test_multi_tile_templates.ps1`, and a full preview `plan_cell_templates.ps1`/`build_cell_vmfs.ps1` regeneration (164/164 cells) all still pass.
