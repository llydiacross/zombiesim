# Centered 2x2 and 3x3 Tile Templates: Implementation Plan

## Goal

Allow square 2x2 and 3x3 tile templates to occupy multiple spaces in the existing 5-by-5 cell grid while producing one centered `func_instance` in the generated cell VMF.

Examples:

- `buildings/tile_commercial_plaza_2x2.vmf` occupies four normal tile spaces, not four instances.
- `buildings/tile_epicenter_1a_3x.vmf` occupies the centered nine-tile block for `The Epicenter`.

`-v1` through `-v5` remain recipe-variation suffixes. The `2x` suffix is reserved exclusively for a template footprint.

## Authoritative Multi-Tile Extension

This section supersedes every 2x-only statement below. The existing sections remain useful implementation detail where they do not conflict with this extension.

### Design Decisions

- The playable recipe remains a 5-by-5 interior grid. Multi-tile assets do not change logical cell size, world navigation, or the reusable-recipe model.
- Version one supports only square `1x1`, `2x2`, and `3x3` footprints. Rectangles such as `2x3` are deliberately deferred because a 90-degree yaw would swap their logical dimensions.
- A 3x3 Epicenter crater is centered at anchor `(1, 1)`, consumes interior coordinates `1..3` on both axes, and therefore has world origin `(0, 0)` in the current 5-by-5 coordinate system.
- A 2x2 asset cannot sit exactly on the odd-grid center. It uses one of four deterministic central anchors: `(1,1)`, `(2,1)`, `(1,2)`, or `(2,2)`.
- `The Epicenter` is an exclusive, high-priority physical landmark. Its source map cell must contain only `The Epicenter`; ordinary landmark records must be relocated or omitted rather than competing with a crater instance.
- The outer border ring is not unused terrain. The builder currently emits it at coordinates `-1..5` as 24 wall, corner, road-continuation, ramp, or carpark-endcap instances. A large template may use that space only through a declared border lease that replaces every affected border instance with compatible geometry. It must never silently remove a border wall.
- A 3x3 crater centered inside the 5-by-5 interior needs no outer-border lease by default. It has a one-tile interior margin on all four sides. First author the crater to fit its declared 3x3 footprint; use an interior or border envelope only when Hammer proves that the visual design needs it.
- Logical cells are separate compiled BSPs. No asset may extend beyond the outer border ring in an attempt to meet geometry from a neighboring logical cell.

### Terminology

| Term | Meaning |
| --- | --- |
| Logical footprint | The `1x1`, `2x2`, or `3x3` interior tile coordinates owned by one placement. It controls overlap, traversal compatibility, and recipe validation. |
| Anchor | The top-left coordinate of a logical footprint. |
| Interior envelope | Extra interior coordinates that a large asset reserves for visual clearance or matching underlay. It remains within `0..4`. |
| Border ring | The independent perimeter generated by `build_cell_vmfs.ps1` at coordinates `-1..5`. It contains 24 instances around the 5-by-5 interior. |
| Border lease | A resolved, named replacement for one or more border-ring instances. It is required before a template may visibly use the outer ring. |
| Physical feature | The one landmark/building/decorative asset selected to own a multi-tile footprint. A logical cell may have multiple map labels, but large physical features need an explicit priority policy. |

### Footprint Naming And Template Metadata

Use an unambiguous canonical filename suffix:

```text
tile_<name>_2x2.vmf
tile_<name>_3x3.vmf
```

Keep `_2x.vmf` as a temporary backwards-compatible alias for `2x2` during migration. Do not infer a footprint from arbitrary text elsewhere in a path. `Get-TemplateFootprint` should recognize only terminal `_2x`, `_2x2`, and `_3x3` suffixes, returning `{ width, height }`.

The filename supplies geometry size. A new explicit feature-policy registry supplies placement behavior; do not duplicate the size in two places unless validation checks that the values agree. The intended settings shape is:

```json
"multiTileFeatures": {
   "maximumFootprint": 3,
   "specialLandmarks": {
      "The Epicenter": {
         "placement": "center",
         "overwriteRoads": true,
         "capApproachRoads": true
      }
   }
}
```

`specialLandmarks` is the explicit opt-in for exceptional physical features. Ordinary landmarks and buildings still fail closed when a footprint touches transport. A flagged feature may claim road roles, and `capApproachRoads` converts every surviving road tile that directly faces its footprint into the appropriate dead-end asset. This keeps the cell-level road connections reachable without letting a road run through the landmark.

### Generalized Coordinate Contract

For an anchor `(X, Y)`, footprint `(width, height)`, cell-grid center `C`, and tile width `W`, the emitted instance origin is:

```text
originX = (X + (width - 1) / 2 - C) * W
originY = (C - Y - (height - 1) / 2) * W
```

| Footprint | Example anchor | Origin in a 5-by-5 cell with `C = 2` |
| --- | --- | --- |
| `1x1` | `(2,2)` | `(0,0)` |
| `2x2` | `(1,1)` | `(-0.5W, 0.5W)` |
| `3x3` | `(1,1)` | `(0,0)` |

The source VMF remains authored around its geometric center. Do not change a native model's `ModelOffset` or bake placement compensation into the source asset; the generated `func_instance` origin owns this alignment.

### Occupancy And Recipe Architecture

The current planner uses one `$placements` entry per interior coordinate, then the builder assumes exactly 25 placement records. Multi-tile support must separate those two responsibilities:

1. Keep an interior `occupancyByCoordinate` map for all 25 logical coordinates. Each entry records its owner, current role, and whether it is protected transport, free terrain, or reserved by a feature.
2. Keep a separate `emittedPlacements` list. A normal tile emits one record; a `2x2` or `3x3` feature emits exactly one record while owning four or nine occupancy coordinates.
3. Add `Get-FootprintCoordinates`, `Test-FootprintAvailable`, and `Reserve-Footprint`. Reservation is atomic: validate every coordinate first, then claim all coordinates, then replace the affected normal tile instances with one macro placement.
4. Add a stable `placementId` to every emitted placement. It lets the plan explain which occupancy coordinates and border leases belong to a macro without serializing duplicate instances.
5. Plan output must materialize `footprintWidth` and `footprintHeight` on every placement. Missing values default to `1` only while reading old plans.
6. Recipe reuse must compare a canonical layout signature containing template, anchor, footprint, yaw, role, and border leases. Two cells may share a BSP filename only when their complete emitted placement layouts are identical.

The target plan record for the initial crater is:

```json
{
   "placementId": "landmark:the-epicenter",
   "tileX": 1,
   "tileY": 1,
   "footprintWidth": 3,
   "footprintHeight": 3,
   "template": "landmarks/tile_epicenter_crater_3x3.vmf",
   "rotationYaw": 0,
   "role": "landmark_epicenter"
}
```

### Planner Order And Compatibility Rules

The planner should move from opportunistic replacement to an explicit reservation pass:

1. Seed 25 interior terrain occupancy slots.
2. Lay down roads, motorways, bridges, ramps, onramps, carpark junctions, and their protected access slots.
3. Resolve a primary physical landmark feature by priority. `The Epicenter` is evaluated before ordinary landmark matching.
4. Reserve and emit any multi-tile feature.
5. Resolve a single-tile ordinary landmark only if a large exclusive feature did not claim the cell.
6. Fill only remaining free slots with buildings and decorations.
7. Add carparks only when their complete entrance/lane/endcap layout remains available. Existing no-carpark-on-landmark behavior remains intact.
8. Derive border placements after the final recipe layout and apply any validated border leases.

Normal multi-tile candidates must fail closed when any owned coordinate is a road, motorway, bridge, ramp, onramp, carpark, safe-zone entrance, or another landmark. A `specialLandmarks` entry with `overwriteRoads: true` is the sole exception: it may reserve transport roles inside its declared footprint, then `capApproachRoads` must replace each surviving adjacent approach with a compatible dead end.

For entrance-bearing `2x2` or `3x3` buildings, road-facing selection must inspect the full exposed edge, not just the anchor tile. An authored north-edge entrance must be aligned with a compatible road segment beside the feature's north edge. The initial crater has no entrance and uses fixed yaw `0`.

### The Epicenter Crater Policy

`The Epicenter` is the first deliberate `3x3` feature because it has a natural centered layout and no road-frontage requirement.

- Update `generate_world_cells.ps1` so radiation-source selection uses a reachable ordinary-road candidate set. Exclude motorways, diagonal highways, the map origin, and any road that cannot remain part of the playable graph.
- When a radiation source is chosen, set its landmark list to exactly `@($epicenterLandmark)` rather than appending `The Epicenter` to ordinary landmarks. This avoids a map icon list that cannot be represented physically by the crater.
- If a deterministic seed has no eligible reachable road cell, report an actionable generation error. Do not place a crater over a motorway or bridge topology.
- In `plan_cell_templates.ps1`, the `specialLandmarks.The Epicenter` policy permits the centered anchor `(center - 1, center - 1)` to replace ordinary road tiles. It then caps all remaining road approaches at the crater perimeter.
- The initial crater occupies only `1..3` in each dimension. Its surrounding tile ring remains destroyed terrain or explicitly configured rubble; it cannot receive generic buildings, ordinary landmarks, or carparks.
- Safe-zone selection must exclude every epicenter cell even if future source-data changes make it technically reachable.

A normal cell may still expose up to four logical landmark names on the world map. In the first implementation it has at most one physical landmark feature, matching present behavior. Later multi-landmark layout work can place multiple small features in unreserved slots, but it must not compete with an exclusive 3x3 crater.

### Controlled Use Of The Border Ring

Large art sometimes needs more visual room than its logical footprint. Support that deliberately rather than treating the perimeter as vacant.

1. Prefer an interior envelope first. For a centered 3x3 crater, the remaining rows and columns `0` and `4` provide a full one-tile margin inside the playable recipe. If the crater rim needs that area, reserve those interior slots and replace their terrain with an approved destroyed-ground underlay.
2. Add outer border use only through `borderReservations` in the resolved recipe. A reservation names exact ring coordinates, owner `placementId`, replacement template, and yaw.
3. `Get-BorderPlacements` must continue to emit one instance for all 24 ring slots. A leased slot receives a compatible feature-edge or containment template rather than being omitted.
4. Reject a lease that touches a corner, an edge road continuation, a ramp exit, or a carpark endcap. The first implementation supports straight non-corner wall replacements only.
5. Reject overlapping leases from separate features. The planner must include resolved leases in the layout signature and diagnostics.
6. Keep all collision, nodraw, skybox, and blocking geometry inside the current map's outer ring. The next logical cell is a different BSP and cannot supply a matching crater wall or terrain slope.

For example, an edge-adjacent 2x2 plaza may eventually request a west-side lease at `(-1, 1)` and `(-1, 2)`. The planner may accept it only if both slots are ordinary west border walls and a purpose-built west facade instance replaces them. The default Epicenter crater requests no lease, so it is a safe first proof of the multi-tile system.

### Builder And Renderer Changes

`build_cell_vmfs.ps1` must:

1. Read `footprintWidth` and `footprintHeight`, defaulting legacy placements to `1`.
2. Validate every footprint coordinate is inside `0..4`, all 25 interior coordinates are covered exactly once, and no footprint overlaps another placement.
3. Emit one `func_instance` per placement where `emitsInstance` is true, using the generalized origin formula above.
4. Replace fixed `25` and `49` instance-count assertions with `tilePlacementCount + borderPlacementCount`. With a normal border and no lease suppression, border placement count remains `24`.
5. Pass explicit `borderReservations` to `Get-BorderPlacements`, validate their compatibility with routes and carpark endcaps, and substitute approved border templates without changing the expected 24-slot perimeter.
6. Calculate cubemap anchors from a placement's geometric center and role, not only its anchor coordinate or filename. `landmark_epicenter` should receive a central cubemap candidate.

`build_cell_map_materials.ps1` must draw a macro placement as one `2x2` or `3x3` rectangle with its label centered on the footprint. It must not render the same macro once per occupied coordinate. The satellite stitcher then inherits correct visuals from local recipe maps. The world-level `landmarks.png` overlay remains cell-based and needs only a distinct `EPI` marker.

`export_runtime_world_data.ps1` does not need macro geometry to keep its current gameplay contract: it exports logical cells and landmark names, not VMF placement coordinates. Add an optional physical-feature summary only if the map inspector later needs to explain a crater's exact footprint.

### Validation Matrix

1. Parser tests: valid `_2x`, `_2x2`, and `_3x3` suffixes resolve correctly; invalid/rectangular names fail with an actionable message.
2. Occupancy tests: a `2x2` covers four coordinates, a `3x3` covers nine, the union covers exactly 25 interior coordinates, and no coordinates overlap.
3. Coordinate tests: assert the generalized formula gives half-tile offsets for each `2x2` anchor and `(0,0)` for the centered `3x3` crater.
4. Feature-policy tests: `The Epicenter` wins over ordinary landmark patterns, is exclusive, replaces allowed ordinary-road roles, and caps every surviving approach. Roads, motorways, ramps, carparks, and safe zones remain forbidden unless an explicit special-landmark flag grants the relevant role.
5. Source-generation tests: every radiation source becomes an Epicenter-only reachable-road cell and no safe-zone map is selected on that coordinate.
6. Border tests: no-lease recipes retain the exact current 24-slot ring; valid non-corner wall replacement succeeds; road, ramp, carpark, corner, missing-template, and conflicting leases fail.
7. Recipe-identity tests: cells sharing a generated BSP filename have the same canonical placement and border-lease signatures.
8. Local-map and satellite tests: each large template has one correctly sized schematic region, no duplicate labels, and no layer overlaps at its footprint boundary.
9. Hammer review: inspect a `2x2` building at all four central anchors and the centered `3x3` Epicenter crater in `generated/src_preview`. Confirm authored entrances, ground contact, collision, lighting, cubemaps, and border replacements before compiling production maps.
10. Determinism test: regenerate the same preview seed twice and compare map manifest, template plan, required recipe list, and generated VMF layout signatures.

### Delivery Sequence

1. Add generalized footprint parsing, plan-schema fields, occupancy validation, generalized instance origin, and dynamic VMF-count validation. Do not enable any multi-tile asset yet.
2. Add a dev-only `2x2` template and a generated fixture recipe. Validate it in Hammer with no border lease.
3. Add `landmarks/tile_epicenter_crater_3x3.vmf`, the exclusive Epicenter source policy, and the centered `3x3` fixture. Keep its art inside its footprint for the first pass.
4. Refresh preview plan, VMFs, local materials, satellite material, staged map layers, and runtime data together. Compile only preview recipes after Hammer review.
5. Add interior envelopes for crater rims or plazas when the asset requires more than its nominal footprint.
6. Add declared border leases and compatible edge templates only after the no-lease system is stable. Keep edge-road, ramp, carpark, and corner leases unsupported until specific authored assets and tests exist.
7. Generalize deliberate `2x2` and `3x3` building/decor policies after the Epicenter proof, never by enabling all filename matches globally.

## Placement Contract

- A normal template has footprint `1x1`, an integer `(tileX, tileY)` anchor, and one instance at that tile's center.
- A `_2x.vmf` template has footprint `2x2`; its anchor is the top-left grid coordinate of the occupied area.
- The source VMF's authored origin remains at its geometric center.
- The generator places the one instance at the geometric midpoint of its occupied 2x2 block.
- Do not alter source VMFs or model offsets to compensate for generator placement.

For a cell-grid center `C` and tile width `W`, a 2x anchor `(X, Y)` has origin:

```
originX = (X + 0.5 - C) * W
originY = (C - Y - 0.5) * W
```

This is the only builder-side coordinate change required for a centered 2x template.

## Data Model Changes

Extend each `tilePlacement` record with explicit footprint data:

```
tileX, tileY          # top-left anchor
footprintWidth         # 1 or 2
footprintHeight        # 1 or 2
template, rotationYaw, role
```

Default missing footprint values to `1`. This keeps existing plans readable during a controlled migration, though the planner should immediately emit the explicit fields for all new plans.

Add one planner helper:

```
Get-TemplateFootprint(templatePath) -> { width = 1|2; height = 1|2 }
```

Initially, detect `_2x.vmf` case-insensitively at the end of the basename. Do not infer size from other filename text. Future `3x` support can generalize this helper without changing placement consumers.

## Planner Changes

File: `bin/plan_cell_templates.ps1`

1. Keep the existing 5-by-5 `$placements` coordinate map as the occupancy source of truth.
2. Add a helper that tests whether all coordinates of a proposed footprint are in bounds and currently eligible terrain/building slots.
3. Add a helper that reserves every occupied coordinate, but emits one placement record anchored at the top-left coordinate.
4. Process transport reservations first, exactly as today. A 2x building or decoration must never replace a road, motorway, bridge, ramp, or other transport tile.
5. During building/decor placement, consider a 2x candidate only when all four spaces are available. Otherwise fall back to the current 1x1 selection logic.
6. Reserve the accepted 2x footprint before continuing the placement loop, so later buildings/decorations cannot overlap it.
7. Use the placement seed when choosing both the anchor and the 2x template, preserving deterministic output and meaningful `-vN` layouts.
8. Keep landmarks conservative initially: use 2x templates only when explicitly selected by the landmark policy. Do not let a generic 2x building replace an existing landmark selection.
9. Recipe identity already incorporates final `tilePlacements`; a 2x footprint will therefore naturally create a distinct recipe whenever its placement differs.

Recommended first scope: generic buildings and decorations only. Add 2x roads, bridges, ramps, and special transport pieces later as separate topology work.

## Builder Changes

File: `bin/build_cell_vmfs.ps1`

1. Read `footprintWidth` and `footprintHeight`, defaulting each to `1`.
2. Keep the current coordinate formula for 1x1 placements.
3. For a 2x footprint, add half of a tile width in X and subtract half of a tile width in Y from the anchored 1x1 origin formula.
4. Keep one emitted `func_instance` per placement record.
5. Replace the fixed validation of exactly 25 `func_instance`s with structural validation:
   - every placement emits one instance;
   - all occupied coordinates are in bounds;
   - no occupied coordinates overlap;
   - total covered grid area is 25.

The generated VMF will contain fewer than 25 instances whenever it uses one or more 2x templates. That is expected.

## Selection Rules

- A 2x candidate may only be anchored where `(X, Y)`, `(X+1, Y)`, `(X, Y+1)`, and `(X+1, Y+1)` fit within the 5-by-5 cell.
- Never place it over non-terrain, road, motorway, bridge, ramp, carpark, or landmark roles unless a later feature explicitly permits that role.
- Prefer anchors that have already been chosen for building density, then reserve their neighbouring eligible tile. This avoids making the map denser merely because a 2x template exists.
- If no valid 2x footprint exists, retain the existing 1x1 behavior.
- A 2x template should count as four covered tiles for occupancy but one placement for VMF output.

## Filename Discovery

No change is needed to the tile-template directory structure. `_2x.vmf` files will be found by the existing recursive template discovery.

The filtering policy must explicitly allow desired `_2x` families wherever it currently selects generic buildings, commercial assets, decorations, or landmarks. This prevents an incidental filename from becoming eligible simply because it exists.

## Validation Plan

1. Add one known 2x test template in a non-production test/dev template location.
2. Generate a small preview plan with a deterministic seed.
3. Assert that the plan contains one 2x placement record with a `2x2` footprint and no overlapping coordinates.
4. Build into `maps/src_preview`, never production `maps/src` during the first review.
5. Assert the recipe's instance count equals its placement-record count, not 25.
6. Open the generated recipe in Hammer and verify that the template is centered across exactly four tile spaces.
7. Regenerate using the same seed and compare plans to confirm byte-stable deterministic output.
8. Confirm that all roads, ramps, bridges, landmarks, and cell borders remain unchanged around the 2x placement.
9. Run the existing preview recipe audit and ensure every cell covers exactly 25 tile coordinates.

## Risks And Guardrails

- Rotation: a square 2x footprint remains 2x2 at every yaw. Rectangular future footprints will need width/height swapping at 90 and 270 degrees.
- Existing builder validation assumes 25 instances. It must be changed before any 2x template can be used.
- The planner must reserve all four coordinates atomically. Partial reservation would cause overlap and malformed recipes.
- Do not modify authored source template origins to solve placement. Correct the generated instance origin instead.
- Do not broaden this into variable-size map cells. `_2x` describes a footprint inside the existing 5-by-5 recipe grid only.

## Estimated Scope

The first 2x building/decor implementation is a contained planner-plus-builder change: approximately two new helpers, a placement-record extension, a reservation step, and replacement of the fixed 25-instance validator. It should be developed and reviewed entirely through the isolated preview pipeline before applying it to production generation.
